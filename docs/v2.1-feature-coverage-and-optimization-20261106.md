# 2.1.0 功能落地情况与优化建议

日期：2026-11-06。源码基线：`main` / `0e4b6ccbd21ca5f73e0d18df3b7a6a8dcbe54dfe`。

## 1. 判断口径与结论

本报告回答“当前基于 2.1.0 实际做了什么、哪些还没形成可用功能、下一步优化什么”。与 [上游同步分析](upstream-sync-analysis-20261106.md) 的版本差异问题分开。

本次对照官方 2.1.0 功能说明，检查当前前端入口、后端路由、运行策略、插件清单、关键服务及近期交付记录，并复跑定向测试。没有检查生产配置、登录真实业务账号、调用模型、发送频道消息、部署或升级。

状态定义：

- **主要链路已实现**：当前源码具有页面、接口和领域处理路径；不等于本次完成所有真实业务验收。
- **部分接入**：有底层代码，但产品入口、功能完整性、依赖条件或多用户兼容存在明确缺口。
- **有意限制**：当前策略主动关闭或缩小范围，不能视作普通漏开发，更不能直接解除限制。
- **待实际验收**：源码存在，但本次没有足够证据确认实际部署、真实账号及外部服务效果。

当前产品的核心是企业多用户智能体平台。对话、身份、智能体授权、技能治理、文件归属、私人记忆和运行恢复已有大量二开。2.1.0 中桌面生态、外部执行器和复杂扩展应用的落地程度相对低；文件中心和知识检索则已具备基础，但还有直接影响日常使用的缺口。

不适合给出单一完成百分比：原版能力、被产品策略限制的能力、多用户新增能力，以及真实外部验收不是同一统计口径。

官方对照：[2.1.0 中文发布说明](https://github.com/agentscope-ai/QwenPaw/blob/v2.1.0/website/public/release-notes/v2.1.0.zh.md)。

## 3. 明确存在的功能缺口

### 3.1 文件中心：文件归属完善，管理操作还不完整

当前 `PersonalLibraryPanel.tsx` 的核心操作是上传、展示列表、点击预览；`FilePreviewPane.tsx:137` 渲染预览组件，没有接入文本保存或版本比较。独立资料库路由目前覆盖保存、上传、列表、读取、下载以及从附件/运行文件/产物导入。

领域服务已经有 `move`、`delete`、`search_text` 等方法。因此可以复用已有权限与生命周期服务，补齐页面和接口，不需要重新建设一套文件系统。

建议优先增加：

- 文件搜索、筛选、分页与明确的下载操作。
- 重命名、移动、删除及确认/失败反馈；删除继续遵循现有归属规则。
- 索引状态：排队、处理中、已完成、失败原因、重试。
- 按需支持 Markdown/TXT/JSON 等文本编辑、修订检查与差异预览。Office 在线编辑不宜纳入第一批。

### 3.2 资料检索：已有索引，但仍以逐文档匹配为主

当前搜索遍历本作用域资料，读取每个文档的 JSON 索引并匹配路径、关键词和正文；缓存缺失时会尝试重新抽取内容。该结构对小资料库简单有效，但资料数量增加时会增加读取与处理成本；本次没有做容量测量，不提供未经验证的耗时结论。

当前 PDF 抽取使用文本层，无文字页面会跳过。扫描合同、扫描标书或图片资料不能因此获得可搜索正文。资料库检索与 ReMe 记忆是两条不同链路：记忆支持 Embedding，不代表个人资料库已支持语义检索。

建议顺序：先做异步增量索引、状态与失败重试、稳定的全文检索，再补 OCR；有足够业务样本证明必要时，再加入分块、向量召回和重排。保留文件名精确命中优先，引用返回文件与页码/段落，并在检索时重新核对用户权限。

### 3.3 图片：上传、预览、模型读取三者限制不一致

`src/qwenpaw/providers/capping_formatter.py:54` 定义 `MAX_INLINE_MEDIA_BYTES = 2 * 1024 * 1024`。`freeze_local_image()` 在读取和转换前后检查这个限制，所以某些图片虽然能够上传和预览，仍不能在这条模型输入路径中被读取。

建议保留原图用于下载，针对模型生成独立的缩放/压缩副本；根据模型能力限制尺寸、像素和字节量，提前显示可理解的提示。应覆盖 EXIF 方向、透明图、长截图和高分辨率图片，不宜单纯无限提高阈值。

### 3.4 插件：平台已升级加载协议，自带包还未跟进

检查当前仓库的 13 个插件清单，6 个声明了前端入口：Agent Kanban、Creator、Chrome、CloudPaw、Computer-use、桌面宠物。它们均未声明 `entry.frontend_runtime = "worker-v1"`。

当前加载器会拒绝这些旧前端入口，并提示升级。这个结论针对仓库中这些包，不能直接推断服务器当前已安装版本及启用状态；也不代表它们的后端工具一律不可用。

建议把“可发现/可安装/已授权/前端兼容/运行就绪”区分展示。先让一个简单应用（如看板）通过当前 Worker 协议完成安装、打开、数据保存、权限隔离、升级保留授权和卸载的闭环，再扩展其他应用。Creator 等复杂应用还需设计与当前隔离要求相容的宿主方式，不能仅修改 manifest 声明或恢复主线程执行。

应用的数据目录、任务、素材、模型密钥和付费操作也需要逐项归属检查。平台允许某用户打开应用，并不能单独证明第三方应用内部数据已按用户隔离。

### 3.5 记忆：优先改善质量和可解释性

已有自动/手动记忆、实际召回事件、Embedding 和重建索引等功能，不应重复开发。

重排在 `reme_light_memory_manager.py` 与配置模型中已经实现，但当前记忆配置卡片没有对应的重排配置表单。可补受控配置、连接校验、超时与降级状态；新增密钥字段必须接入当前凭据管理。

建议用业务问题建立回归样本：应该召回哪份文件、是否引用正确、旧记忆是否被误当当前事实、是否跨用户、无相关资料时是否明确说明。让页面区分未配置、正在索引、索引失败、没有命中，避免用户把这些状态都理解成“智能体不记得”。

## 4. 不宜直接补回的功能

### ACP 与外部执行器

当前 `_retire_acp_config_write_routes()` 在应用组装时移除 ACP 写路由，旧函数定义仍保留；不能只看到路由装饰器就断言 API 可写。本次 OpenAPI 契约测试确认只读兼容、Harness/MCP 读取保留、新工作区不注册旧委托工具。

如果业务确实需要外部编码智能体，应单独确定：每用户凭据、执行进程与工作目录归属、审批透传、取消、输出持久化和资源配额。新建界面补后端选项应在这些契约明确后进行。当前分析不把恢复 ACP 当成默认优化任务。

### Browser-use 与 Computer-use

隔离 Browser 有现成策略和限流，可在业务需要时通过管理员受控开启，并完成真实网页测试。连接用户已登录 Chrome 属于另一种凭据与端点信任方案，不能通过取消 incognito/headless 限制来实现。

Computer-use 需要用户端授权设备、会话归属与接管机制。对于当前网页平台，应先明确要操控的是服务器还是用户电脑，再确定是否值得投入；优先级低于文件和检索。

### OS Shell 和界面扩展

窗口式桌面入口仍存在，可补多账号切换和状态恢复验收；在实际可用应用较少时，优先改善核心操作而非继续增加桌面装饰。主题、字体和布局可以参考后续版本，但不应牵动登录、路由及插件隔离。

后续上游的模型路由、媒体上下文处理、审批竞态、技能下载等可作为实现参考。已有会话分页、身份切换、严格 Worker 和登录续期恢复应作为回归约束，不能为跟进上游而丢失。
