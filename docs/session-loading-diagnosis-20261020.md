# 会话查看缓慢的只读诊断

## 范围

本轮仅检查线上现状：读取已有 Nginx 日志、容器健康与负载，在显式 `READ ONLY` 事务内执行 SELECT，并读取已有消息载荷文件。没有修改线上配置、代码和业务数据，没有签发临时登录或调用会产生管理员查看审计的接口。诊断程序、统计结果和本文仅保存在本地。

## 已确认的事实

- 服务健康；8 核机器的 load average 约 0.5。该时点未见 CPU 饱和，但单次采样不能排除其他时段的负载波动。
- 日志中普通会话历史响应达到约 15.3 MB，管理员详情响应达到约 17.1 MB。日志数值为已发生请求的响应字节数，不含本轮新发起的认证请求。
- 选取四条较大的现有会话，在只读事务内测量消息查询及共用历史投影。查询约 4.5–10.1 ms；样本消息还原约 1.8–78.4 ms。还原后的数据大小见下表。

| 样本 | 原始记录 | 有效消息 | 查询 ms | 历史还原 ms | 展示历史 JSON 大小 | 含原始记录的详情 JSON 大小 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 321 | 321 | 10.10 | 78.37 | 18,549,485 B | 19,355,725 B |
| 2 | 138 | 138 | 6.56 | 1.80 | 734,462 B | 1,509,792 B |
| 3 | 193 | 145 | 4.55 | 8.20 | 3,192,703 B | 3,643,055 B |
| 4 | 214 | 214 | 5.41 | 31.38 | 11,681,176 B | 12,198,397 B |

上表 JSON 大小为只读程序使用现有消息投影后编码得到的测量值，并非浏览器当前那一次请求的完整 HTTP 耗时。编码测量为约 34–473 ms，包含诊断中的两份数据编码开销，不能直接当作接口服务时间。

样本 1 读取了 20 个外置载荷文件，合计 17,840,838 B；最大的三条消息均为 `plugin_call_output`，各约 2.2 MB。样本 4 同样以大型工具输出为主。主要数据量来自工具返回内容，而非普通对话文字。

## 代码路径

1. 普通会话列表的 `handleView` 先等待 `inspectSessionForView`。后者调用完整 `getChat`，仅以 `messages.length` 判断是否为空。完整历史下载和解析结束前不会跳转，也没有这次等待专用的按钮忙碌反馈。
2. 跳转后聊天页的 `fetchAndBuildSession` 有独立 `getChat` 请求入口。前面的检查没有把历史放入该页面的转换缓存；首次打开时可能重复下载。此结论来自代码路径，尚未使用用户的已登录浏览器逐次验证请求次数。
3. 后端历史查询没有消息分页，会读取并还原整段历史，包括外置的大型工具输出。工具卡片即使只显示摘要，完整数据也已传输到浏览器。
4. 管理员详情同时返回 `messages` 和 `history_messages`；原始记录即使未打开也会随详情传输。两份数据重叠程度因会话存储形式不同而变化，并非所有会话都正好翻倍。
5. 管理员聊天视图通过 `turns.map` 一次渲染全部消息和工具卡片，没有按视口限制渲染范围。这是确定的实现特征；浏览器端具体渲染耗时尚未直接测量。
6. 首屏仍存在已发现的 Monaco 同步加载、全站页面提前导入和空加载状态问题，首次进入时可能与历史加载叠加。此前线上 gzip 与缓存仅修复了静态资源传输配置，没有改变这些源码路径。

## 判断

现有证据支持的主要瓶颈是全量大响应、跳转前等待、潜在重复获取及全量渲染。四个样本的数据库查询均很快，不能把当前慢现象笼统归因于数据库或服务器算力。

公网传输会放大大响应的等待，但本轮没有测量用户当前网络，也没有把此前脚本下载速度直接换算成会话请求的确定耗时。

## 待本地修复和验证

1. 用轻量消息存在性信息替代跳转前的完整历史检查，及时显示目标页面和加载状态，避免首次重复请求。
2. 历史按页或按完整对话轮次读取；大型工具输出先返回摘要，完整输出在展开时获取，保留原始数据与权限检查。
3. 管理员原始记录改为切换后再读取；长会话增加分批或可视区域渲染。
4. 首屏按需加载编辑器、页面和插件依赖。
5. 在本地以 321 条记录、单条工具输出超过 2 MB 的规模验收：比较请求次数、响应字节数、首批内容展示时间和滚动表现，并覆盖普通用户与管理员隔离。

本轮没有实施上述源码修复，也没有提交、推送或部署；按用户要求，后续先在本地实现并展示验证结果，获得确认后再处理 Git 和上线。
