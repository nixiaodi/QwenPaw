# 最新用户消息编辑：实现与本地验收

日期：2026-10-14。用户确认设计后实施；本次仅更新本地服务，没有提交 Git、推送或部署生产服务器。

## 用户行为

- 最新用户消息的复制按钮旁新增铅笔按钮，较早的用户消息不提供编辑入口。
- 原位编辑文本，支持取消、重新发送、Escape 取消和 Ctrl/Cmd+Enter 发送；不允许空文本，长度上限 10000 字符。
- 等待启动、生成中、停止后和完成后的轮次使用相同修订入口。取消编辑不停止原回答；确认重发才停止原轮次。
- 保持会话和智能体，沿用当前模型与审批设置，保留原消息的图片、文件等附件。
- 重发后旧轮次不再进入有效聊天记录和模型上下文，刷新后仍显示新轮次。原始记录保留用于审计。
- 失败保留编辑草稿；过期编辑返回冲突，断线后重复提交相同修订请求不会再次调用模型。
- 切换会话或智能体清理待发送编辑，避免旧提交占用或覆盖新会话。

## 实现范围

### 前端

`LatestMessageEditor` 负责编辑器和按钮，`latestMessageEdit` 负责最新消息匹配及文本替换。沿用现有聊天组件和流式传输，局部更新消息，无需重新挂载整个聊天页面。

服务端提供稳定消息 ID 和 `qwenpaw_editable` 能力标识；只读会话及不支持修订的外部后端不展示入口。服务端再次校验所有权与最新消息，前端按钮不是权限边界。

### 服务端

Console 的普通提交与编辑提交使用同一会话提交锁。普通提交先持久化用户消息和待执行运行，再启动后台流；编辑提交校验预期消息、停止原任务、保留审计事实、恢复执行前上下文并启动新运行。

PostgreSQL 沿用现有消息状态，将旧轮次标为 `superseded`，无需数据库结构迁移。修订请求 ID 对应确定的运行 ID，实现幂等；重复请求附着已有运行或回放既有事件。终态回放保留已输出内容，避免额外插入空响应错误。

每轮保存执行前 JSON 上下文及 Scroll 序号水位。编辑时恢复该边界，并清除 Scroll 有效历史和全文检索中的被替代内容；正常保存和取消保存携带运行版本，阻止旧任务延迟保存覆盖新上下文。

附件以原数据库记录为准保留并映射到所属会话附件接口；编辑后的内容重新转换成运行时的类型，确保频道输入适配器能实际读取文本和附件。已导入 PostgreSQL 的旧用户消息使用稳定记录 ID；无法可靠恢复的旧上下文返回明确错误，不猜测或清空此前对话。

## 明确边界

- 编辑当前实现的是文本替换，原附件保留；不增加附件编辑和历史分支切换功能。
- 旧回答和旧工具消息退出有效对话，但已发生的发信、文件写入、数据库操作、记忆写入等实际效果不会自动撤销。
- 本次不修改生产服务，也不承诺没有测试覆盖的外部后端支持此功能。

使用现有存储状态、聊天提交链路与审批机制，避免新增迁移和重复执行逻辑；输入编辑、轮次协调、存储修订和上下文恢复分别承担独立职责。

## 旧会话带附件编辑补修

针对用户反馈的本地旧会话，只读检查确认它创建于编辑功能上线前，没有执行前快照。原始用户输入包含文本和文件；运行时在文件媒体块后增加了“用户上传文件，已经下载到……”文本。因此，旧上下文的全部文本与原始用户文本不相等，恢复失败返回 `turn_context_unavailable`，前端又将所有 409 错误统一显示为“最新消息已发生变化”。

本次修改：

- 恢复旧轮次时，只排除紧邻媒体块且路径与原附件一致的中文或英文系统说明。用户原文仍须完整匹配；不同路径、额外用户文字和非相邻说明不会被忽略。冻结图片使用数据库原附件路径验证，不依赖内嵌图像是否仍保留 URL。
- 从原消息和所属会话附件记录取得路径，兼容受保护附件 URL、文件 URI 与 Windows 路径。保留所有权、最新消息及运行版本校验。
- 前端区分上下文恢复失败和真正的最新消息冲突，不再建议无法解决问题的重复刷新。
- 编辑框继续展示原文件、图片等附件，并提示这些附件会随修改后的消息一起发送。附件展示复用原消息媒体组件；文本替换仍由服务端保留原附件。
- 上传入口使用通用文件说明，去掉依据模型原生多模态能力产生的“只支持图片”和相关警告，保留上传大小限制。

验证：相关后端回归 230 项通过，旧输入恢复专项 11 项通过；PostgreSQL 集成扩展为 7 项通过（包括无快照的旧文件轮次恢复与附件归属）；前端 12 个测试文件、89 项通过。补修后原会话的只读预检成功识别恢复边界 557，原文件保留并映射到受保护附件 URL；未改写原会话记录。

已重新构建前端并重启本地 18089 服务，继续使用本地环境测试。本次仍未提交、推送或部署生产服务器。

构建后的页面再次通过 6 个浏览器场景：编辑框同时展示原文件和原图片，取消、重新发送、失败恢复、断线重试和切页均正常；重发请求保留这两类附件。另已验证图片原生能力模型下可上传文本文件，上传入口无文件类型限制，也无“仅支持图片”或多模态能力警告。服务首页与最新构建静态资源一致，8 个启用智能体均正常响应。

## 重发附件即时显示与上游断流补修

本次再次核查同一会话，确认 13:01 的编辑请求已正确接收并创建新运行，实际选择 `cpa / gpt-5.6-sol`。错误发生在后续模型请求生成第二个工具的参数期间：8317 代理虽然返回 HTTP 200，流内却返回 `stream disconnected before completion: stream closed before response.completed`。现有证据确认模型响应未完成，不能进一步断言是网络、代理还是上游模型服务内部的哪一环主动中断。

两个问题分别来自不同环节：

- 前端重发只向 SDK 提交了文本；原附件在异步模型检查之后才补进请求，因此乐观消息的第一帧缺少附件。现在将原附件转换成已上传完成的 SDK `fileList`，创建新气泡时同时带入文件、图片等媒体，不重复上传。服务端仍以原附件记录为准保留内容和权限。
- 断流被 SDK 包装成没有 HTTP 状态码的基础 `openai.APIError`，原重试分类没有识别这种错误。错误展示读取的是旧模型属性，实际 SDK 使用 `.model`，因此把有效模型误写成 `unknown`。

统一模型调用层现在识别这两种未完成流错误。工具参数在该次模型响应结束前暂存；失败时丢弃该尝试的工具 ID 和参数增量，再按现有次数和退避配置重试当前模型子请求。此前已执行的工具不重新执行。成功后按照原顺序透传全部增量和完整末帧，兼容实际 AgentScope `ChatResponse`、`ChatUsage` 及复用可变响应对象的情况。

普通文本首帧仍直接传递。已经传递文字或思考内容后遇到这种断流，不将另一尝试的内容拼接到原回答中；持续失败仍会明确报告错误。错误提示现在读取真实模型名。取消停止重试并释放并发槽；SDK 将取消转换成 interrupted 末帧时，Agent 在工具调度前退出。

另外修正 PostgreSQL 运行终态：最终 `response.status=failed/cancelled` 可以覆盖前面已完成的消息状态，避免模型流失败后运行被记为完成；工具自身的失败不会错误终止整轮运行。新增集成测试先证明旧逻辑的三种终态误判，再验证修复，不改写原用户会话数据。

本次最终验证结果：

1. 后端相关单元回归 269 项通过，另 5 项真实 SDK 响应专项通过，共 274 项。
2. PostgreSQL 会话事件及最新轮次修订集成 18 项通过，使用专用测试数据库及独立临时 schema。
3. 前端相关 12 个测试文件、80 项通过；TypeScript、生产构建、Monaco 样式及改动空白检查通过。
4. 构建后的 18089 页面通过 7 个浏览器场景。新增场景主动延迟模型检查请求，在聊天提交请求尚未发出时，已显示修改后的文本、原文件标识及原图片，且没有重复上传。
5. 重启后的服务通过真实模型两轮验证：带文件发送、编辑重发、重复同一修订回放。有效历史只有新用户消息，原附件保留，旧输入退出执行上下文，旧轮次保留审计，重复请求没有新建模型运行。测试会话归档，临时认证撤销。
6. 本地服务已重启至最新代码，首页及静态资源与本次构建一致，8 个启用智能体正常响应。没有提交、推送或更新生产服务器。
