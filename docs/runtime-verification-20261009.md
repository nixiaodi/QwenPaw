# 2026-10-09 技能加载、认证与模型可用性修复

## 已确认的原因

- 旧运行时在模型执行前注入技能正文，并提供了 imagegen 的脚本提示，模型可以直接执行而不调用 `load_skill`。
- 原 `load_skill` 返回 `ToolResponse`，当前 AgentScope `FunctionTool` 会将它转为对象的字符串表示。已改为适配层支持的 `ToolChunk`，保留结构化 JSON 和失败状态。
- 多标签页共享刷新 Cookie，却没有协调轮换。一次刷新同时替换访问令牌与刷新令牌，另一个标签页的旧请求可能因此返回 401。刷新、登录、退出和启动身份验证现在使用同源 Web Lock；身份验证在刷新锁内完成，并通过 BroadcastChannel 同步内存令牌和退出状态。
- 前端发送前的模型检查把所有异常解释为“模型未配置”。现在保留真实错误和 HTTP 状态，只有实际没有默认模型时才显示配置提示。
- 原供应商禁用按钮尝试清空 API Key；无须 Key 的 OpenCode/Kilo 没有有效开关，原配置更新也会忽略空字符串。现为供应商与模型增加独立、持久化的 `enabled` 状态，禁用保留配置。
- HTTPS 部署仍保留 HTTP 阶段的 `QWENPAW_SESSION_COOKIE_SECURE=false`，Compose 与服务配置均已改为 true。

## 当前运行方式

模型先看到当前智能体已启用技能的名称和描述，自己选择技能，再调用 `load_skill` 获取正文。自然语言请求不由运行时指定某个技能或脚本。通用中间件在要求加载技能的任务中阻止先执行后加载；脚本引用另一技能目录时也需要加载该技能。明确的技能命令和多轮任务仍保留用户选择，但不提前加载正文。

禁用的供应商或模型保留在管理页面，可重新启用；可选目录和后端模型解析均检查启用状态。OpenCode、Kilo Code 已在服务器禁用。禁用正在作为默认模型的配置不会自动切换到其他模型，会明确返回不可用原因。
