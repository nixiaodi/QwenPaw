## 5. 差异规模与合并预演

当前 HEAD 与这些上游目标的共同祖先为 `aa1152a0acbb54bccf2d07b438b41f1d26d3bb3e`，即 2.1.0-beta.5 的提交。当前包含的正式版发布说明提交 `e4995dcf5` 不在上游当前主线祖先链中，所以共同祖先落在该 beta 标签；这不否定当前包含正式版 2.1.0 提交。

从共同祖先计算，本地侧改变了 1,546 个路径。对比结果如下：

| 目标 | 上游侧独有提交数 | 上游改变路径数 | 与本地改动重叠路径数 | 模拟合并冲突文件数 |
| --- | ---: | ---: | ---: | ---: |
| v2.2.0 | 190 | 1,747 | 282 | 150 |
| v2.2.1 | 247 | 2,299 | 339 | 202 |
| v2.2.2.post1 | 422 | 3,804 | 423 | 280 |
| upstream/main `2cf28d14a` | 562 | 4,946 | 450 | 328 |

统计说明：

- 提交数采用 `git rev-list --left-right --count HEAD...目标` 的上游侧数量。它包含发布、合并、文档等历史，不等于未实现功能数量；人工移植的等价实现也不会因此消除 Git 图上的差异。
- 改变路径数通过共同祖先两侧的 `git diff --no-renames --name-only` 统计；移动会按旧、新路径计算，包含测试、文档、插件与构建文件，不应据此估算同等数量的核心代码修改。
- 冲突数来自 `git -c merge.renameLimit=10000 merge-tree --write-tree --name-only --no-messages HEAD 目标`。该命令创建临时 Git 对象，不改变 HEAD、索引或工作区，不执行实际合并。
- 自动合并成功的文件仍可能存在语义或权限冲突；上述数量是文本合并结果，不是完整适配工作量。
- 原始统计和稳定版/开发版冲突路径保存在忽略目录 `build/upstream-analysis-20261106/`。

稳定版的冲突集中在 Console 页面（104）、后端 app（36）、前端 API（23）、Agent 运行相关代码（14）、前端组件（11）等区域。直接覆盖上游文件会触及当前核心二开。

## 6. 必须保留或单独设计的兼容边界

### 6.1 当前多用户平台与 Hub

当前平台以 PostgreSQL、可信 ActorContext、用户/Agent 授权和私人工作区为核心；同一平台服务承载共享 Agent、成员关系、私人会话及管理员治理。

上游 Hub 具有独立的用户认证和运行实例控制面，管理本地进程或 Docker runtime；其 RuntimeSpec/RuntimeRecord 包含 owner_user_id 与运行实例生命周期。它与当前架构不等价。直接引入会带来身份、凭据、运行生命周期和代理授权的重复体系。

建议在本轮同步中保留当前身份、授权和数据模型。若以后选择 Hub，需要单独讨论用户、Agent、会话、技能发布、文件、Secret 和运维迁移，不能将其当普通功能开关。

### 6.2 认证、会话与性能

冲突涉及 `console/src/api/request.ts`、`console/src/App.tsx`、聊天页面以及 `src/qwenpaw/app/chats/api.py` 等。需要保护：

- 访问令牌更新后使用新令牌、并发续期合并、临时网络故障恢复、登录页正确跳转。
- `/api/chats/page` 的服务端搜索与游标授权、管理员读取所有会话、深链接解析。
- 历史分页、大工具结果摘要与按需展开、跨用户和跨会话的迟到响应隔离。
- 队列发送所有权、取消、流结束状态、推送订阅及后台监听线程隔离。

上游也有懒加载、工具输出和轮询优化，但不能直接替换当前实现；应比较行为和缺口后移植。上游 SQLite 历史优化也不能代替本地 PostgreSQL 会话权限与持久化逻辑。

### 6.3 技能、插件和文件

当前技能池有草稿、发布申请、公用发布、显式 Agent 授权和用户私人技能。上游批量分发和市场变化需要接入这些服务端授权规则。

当前 `console/src/plugins/usePluginLoader.ts` 明确要求 `frontend_runtime = "worker-v1"`，插件在 Worker 执行。稳定版上游仍通过 Blob URL 动态导入前端模块。直接替换加载器会改变已明确选择的执行隔离策略；新版应用或插件必须逐个验证并适配接口，不能仅修改清单声明。

终端、持久工作区与 PawPort 导入会创建或访问文件及配置；必须使用当前受控路径解析、用户×Agent 归属、Secret 引用和审计机制。

## 8. 推荐推进顺序

1. **以 v2.2.2.post1 固定比较目标。** 按 2.2.0、2.2.1、2.2.2 的功能演进顺序整理差异，标记已等价实现、待移植、需适配与暂不采用；不要求每个中间版本都部署。
2. **优先安全与稳定性。** 从上表技能路径、MCP 响应、构建依赖开始，再处理审批、上下文与模型流。每批保留当前多用户约束并执行定向回归。
3. **分模块接入功能。** 依次评估模型发现与路由、技能市场与版本、界面体验，再评估 Mail/Data/Creator、终端和 PawPort；插件兼容与资源权限作为入口条件。
4. **单独处理架构变更。** Hub、ReMe/Auto Fin、记忆插件化、2.3 频道子进程改造分别立项评估，不与普通体验修复混合。
5. **建立长期同步记录。** 记录每次审查的官方 tag/SHA、已移植补丁、保留的二开差异和测试结果。版本展示区分平台发行版本与已验证的上游基线，避免只看单一版本号误判。

后续验收至少覆盖：管理员与普通用户双身份；共享 Agent 下私人会话/文件/记忆隔离；登录续期与身份切换；会话分页和历史工具输出；技能公用/定向授权/发布申请；MCP 取消与凭据变化；Worker 插件阻塞隔离；审批和后台任务归属；生产构建及恢复流程。

本次仅完成远程配置和静态分析/合并预演，没有运行升级后的应用或测试套件。历史对话中的测试及部署结果属于当时记录，不能当成本次升级验收。建议下一阶段先实施稳定性补丁批次，再推进完整的稳定版兼容同步。
