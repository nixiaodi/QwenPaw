# upstream v2.2.0 合并记录

## 合并目标

本次升级以当前多用户平台为主线，将 `upstream/v2.2.0` 的通用能力合入 `dev-my-fix`，同时保持用户、智能体、会话、文件、技能、插件、模型、自动化和审批数据的现有隔离边界。

上游 `v2.1.1-beta.1` 至 `v2.2.0-beta.7` 的演进内容已通过标签和差异审查纳入评估。beta 标签不单独生成提交或标签，正式版 `v2.2.0` 形成独立合并提交和项目标签。

## 架构决策

### 继续使用现有多用户运行时

当前项目是在一个服务和一个 PostgreSQL 身份域中运行多个用户及多个智能体，授权和数据范围由平台统一控制。上游 QwenPaw Hub 的做法是为每位用户管理独立的 QwenPaw 运行实例，并通过本地进程或容器提供控制面。两者在身份来源、服务生命周期、工作区根目录、凭据和路由方面会形成两套并行控制面。

因此，本分支不启用 QwenPaw Hub，也不包含其控制服务、Hub 登录态、Hub 页面、Hub CLI 和 Hub 部署文档。团队协作继续使用当前多用户架构，避免同一用户同时存在平台身份和 Hub 实例身份。

### 多用户关键域以当前实现为准

下列模块保留现有实现，并只吸收可以证明不会破坏隔离的上游改动：

- 聊天会话、消息恢复、流式状态和重复渲染治理；
- 统一文件中心、个人资料库、产物、临时附件和记忆；
- 智能体配置、模型默认值和共享应用授权；
- 技能池发布、授权、广播和普通用户申请；
- 插件治理、备份、Token 统计和管理员页面；
- PostgreSQL 会话、MCP、自动化、审批和用户归属关系。

## 已合入能力

- QwenPaw Mail 的配置、访问控制、监控服务、驱动卡和控制台入口；邮件监控以单个智能体工作区为生命周期边界注册。
- MCP Streamable HTTP 双协议客户端，并保留多用户模式下的 PostgreSQL 驱动卡与凭据隔离；凭据轮换时支持重新连接无 `reload` 方法的新客户端。
- 模型提供商、故障转移、重试、媒体能力和 AgentScope 2.0.7 兼容更新。
- 模型包装器继续透传 formatter，避免媒体输入能力在 Token 统计、重试和故障转移包装后丢失。
- 批量工具执行、频道、桌面端、Creator、网站和发布说明中的无冲突更新。
- Mail F1 探索模式；每一步工具调用强制严格审批，同时保留当前平台的审批用户归属、会话归属和自动化授权快照。
- QwenPaw Data 的独立包和构建发布材料。其 PawApp 运行时接入暂不启用，待补齐用户及智能体授权模型后再开放。

## 有意未合入或延期的内容

- QwenPaw Hub 控制面及其前端、CLI、部署和测试代码。
- 上游聊天分组和侧栏改版。当前聊天页面包含多次针对跨标签恢复、重复消息和会话身份的修复，直接替换会造成状态模型回退。
- 上游技能池自动同步模型。当前平台已经实现管理员发布、授权、广播和用户申请审批，继续使用现有治理语义。
- 上游 PawApp 上下文重构和 QwenPaw Data 的直接启用。上游上下文未包含当前共享应用的用户授权边界。
- 上游备份流式接口。当前多用户内容备份和恢复范围保持不变。
- ReMe 0.4.1.10、`reme-auto-fin` 和 `reme-daily-paper`。现有按用户、按智能体的记忆扩展依赖 ReMe 0.4.1.5 的组件注册生命周期，升级会在导入阶段触发冻结注册表错误。

## 冲突处理

- 对 113 个文本冲突文件逐一按“多用户边界优先”处理，没有使用上游单用户版本覆盖当前实现。
- 将上游 ServiceManager 的发布式生命周期与当前多用户 Workspace 工厂适配，防止服务启动取消时产生无主实例。
- 邮件监控注册到智能体 Workspace，并在启动前校验后端、推送模式和凭据完整性。
- Mail F1 审批增加 reasoning 展示字段，但继续传递 `approval_user_id`、`conversation_id` 和 `run_id`。
- MCP 新客户端接入后继续执行当前作用域凭据刷新和 PostgreSQL 卡片存储逻辑。

- Python 编译检查：通过。
- 多用户关键回归：`136 passed, 3 skipped`。

## 后续约束

后续若要启用 Hub 或 QwenPaw Data，必须先给出与现有身份表、Agent 授权、个人资料库、产物目录、记忆范围和管理员审计一致的映射方案，不允许在现有多用户服务旁再引入未受治理的第二套用户空间。
