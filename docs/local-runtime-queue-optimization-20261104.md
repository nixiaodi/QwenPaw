## 原因与优化顺序

### 1. 优先消除后台监听与网页请求的线程竞争

此前只读检查中，线上磁盘剩余约 29.96 GB，CPU、内存和数据库健康。服务器本机读取入口文件约 0.002 秒，但经应用发送需要数秒；异步认证接口快，同步接口和静态文件响应出现等待。

线上观察到 40 个目录轮询线程，AnyIO 共享工作线程默认容量也为 40。安装源码确认 `watchfiles.awatch` 长期等待目录变更时使用该共享池，静态文件读取和同步请求也需要同一组名额。本地对照复现了竞争机制。未向线上注入统计，因此没有直接读取线上当时借用的线程名额；不能将本地实验等同于完整线上压测。

本次新增统一的 `isolated_awatch`：每个监听使用自己的单线程执行器等待文件变化，不占用 AnyIO 网页请求线程，也不占用 asyncio 默认执行器。每次只读取一批事件，保留反压，避免无限事件队列。

普通记忆目录、根 MEMORY.md 和工作区文件流共用该实现。ReMe 的路径过滤、事件合并与索引派发规则继续复用，未修改第三方安装包、线程池总容量、数据库结构或索引数据。停止、取消、路径异常和索引派发失败时均关闭监听并回收线程。

本地对照：同一 4,561,243 字节文件，默认共享容量保持 40。

| 场景 | 监听占用共享名额 | 文件响应时间 |
| --- | ---: | ---: |
| 原实现，40 个监听 | 40 | 10.0327 秒 |
| 新实现，40 个监听 | 0 | 0.0106 秒 |
| 新实现，60 个监听 | 0 | 0.0149 秒 |

这是本机隔离实验，不包含公网、完整登录业务和生产实际负载，不承诺线上达到相同绝对耗时。

### 2. 修复队列发送权异常后无法恢复

原逻辑会吞掉浏览器锁接口异常，并在 300 毫秒后把“没有取得锁”当作“其他标签页持锁”；之后不会重新申请。即使只有一个页面、实际没有任何锁，也可能一直只入队。

用户提供的浏览器快照为 `held=[]`、`pending=[]`，当时后端任务已结束，没有运行中或排队任务。该现象与上述失效路径一致，但没有捕获用户原浏览器最初的异常，不能断言其具体异常类型。

本次实现：

- 区分检查中、已获得发送权、确有其他持有者和锁接口异常。
- 锁接口失败及锁被占用时自动重试；页面重新获得焦点或恢复显示时重试。
- 错误提示不再伪称存在其他标签页，提供手动重试入口。
- 保持原锁名称与互斥约束，不强行抢占其他页面的锁，兼容旧页面。
- 切换会话、用户、智能体和卸载时释放发送权、清理过期重试；只读页面不取得发送权。
- 聊天输入组件尚未就绪时保留队列并稍后再试；发送锁暂不可用时重新安排发送。
- 实际发送前重新检查当前会话、发送权、暂停/错误状态和队首消息，避免过期异步回调发送。

修复针对已复现的前端失效路径；没有恢复或修改线上用户队列、会话和历史消息。

### 3. 后续性能优化建议

下一阶段可将静态发布产物交由 Nginx 直接发送，使其进一步独立于 Python 业务进程；同时缩小登录公共入口，按需载入插件依赖和语言包。需要先在本地准备及验证发布配置、插件兼容和页面刷新行为，再按验收后的流程部署。

本次没有把入口文件体积优化宣称为已完成。当前入口仍约 4.56 MB（构建 gzip 约 1.32 MB），它会放大冷缓存时的网络成本。线上已有 gzip 和静态缓存；此前有效浏览器测量显示普通缓存刷新约 0.95～0.99 秒，因此不能笼统认定缓存失效。

## 用户验收

1. 在本地登录，刷新登录页、技能池、菜单和聊天页，确认等待和白屏现象。
2. 单页打开会话，在上一轮完成后发送新问题，确认能继续发送，不误报“其他标签页”。
3. 生成过程中连续输入问题，确认队列依次发送；暂停后应继续保留，恢复后发送。
4. 两个标签页打开同一会话，确认仅一页负责实际发送；关闭持有发送权的页面，另一页可以接管且不重复发送。
5. 切换智能体、会话及用户，检查队列归属与历史展示。

验收通过后，再单独执行提交、推送和线上部署，并在生产环境复测冷缓存、普通刷新、登录后业务接口和队列行为。
