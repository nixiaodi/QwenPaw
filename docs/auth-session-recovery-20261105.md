## 已复现的问题

1. 业务调用方将 `Authorization` 和智能体作用域一并放入请求参数。旧请求层重试时保留调用方的 Authorization，导致刷新成功后仍使用旧令牌，再次收到 401 后直接清空会话并跳转。
2. 刷新函数将所有异常转换成 false，请求层将网络失败、超时和 503 等暂时故障也当成会话失效。自动刷新失败后没有恢复重试安排。
3. 登录页只检查认证是否启用，随后无条件将全局 phase 设为 anonymous；既没有保留已有登录状态，也没有用有效刷新 Cookie 恢复身份后返回首页。
4. 首次恢复身份遇到网络故障同样进入匿名状态，容易把暂时不可达显示成需要重新登录。

本地真实 request → refresh → 状态更新路径已复现前两类误退出；登录组件回归已复现第三类。红灯日志保存在忽略目录 `build/auth-recovery-20261105/repro.log` 和 `repro-headers.log`。特别是“刷新返回 200，但捕获的旧请求头再次触发 401”的复现与线上时序吻合；由于没有用户浏览器的请求头证据，不将它描述为对现场每个请求的唯一归因。

## 本地修复

- 多用户请求每次发送和重试时都从当前身份读取 Authorization，清除参数中捕获的旧令牌；保留调用方原有的智能体、会话及文件作用域。身份已经清空时不能继续使用旧请求参数中的凭据。
- 迟到的旧令牌 401 优先使用已更新令牌重试，不再次无谓轮换；限制重试次数，继续保护取消和身份切换边界。
- 保留刷新接口的 HTTP 状态，仅明确认证拒绝才退出；网络异常、超时、服务暂时异常保留本地会话，按 5、10、20、30 秒上限退避恢复。并发请求共用一次刷新，失败退避期间不会形成刷新风暴。
- 成功刷新后，如果某个业务接口仍返回 401，仅将该请求报告为失败，不凭该接口的响应清空整个平台登录。
- 登录页复用统一身份恢复。已有登录或有效刷新 Cookie 时自动返回 `/chat`；合法站内 return path 保留，外部地址、登录页自身及异常路径回落首页，避免循环跳转。
- 明确退出或 Cookie 确实过期仍显示登录表单。临时无法确认身份时显示重试提示，网络恢复或用户点击后可继续确认，无需误导用户重新输入密码。
- 合并并发启动检查；迟到的启动响应不能覆盖明确退出或新的登录操作。没有降低服务端认证检查，也没有延长或取消服务端有效期。

实现复用现有认证、请求和状态管理层；HTTP 认证拒绝分类与启动提示分别封装，避免业务页面各自实现续期、退出及错误判断。

本地人工验收：

1. 正常登录后手动输入 `/login`，应返回首页；已登录浏览器直接打开登录地址，同样恢复身份后返回。
2. 在聊天或文件页面持续使用超过 15 分钟，续期过程不应切走当前页面。
3. 短暂断网后恢复，应继续使用原会话；页面首次检查身份时遇到故障应显示重试，而不是直接出现密码表单。
4. 主动退出后仍应停留登录页；账号被禁用、会话被撤销或刷新会话确实过期时仍需重新登录。

自动化与合成浏览器验证不代替生产网络及真实账号验收。此次线上只读检查没有保存明文认证信息，原始诊断文件未纳入 Git。
